# Tactical board - follow-ups

Deferred items from the alternative plan discussion (see
`floorball-board-clone-plan.md` for the original tactical-board.com
reference plan we're drawing inspiration from). Everything here is
explicitly out of scope for the MVP but worth revisiting later.

## Sharing / persistence

- **URL-fragment share hits ~32 KB browser limit.** Rough capacity:
  ~20 keyframes with ~10 chips fits; longer animations don't. MVP
  ships fragment-encoded share links + a JSON download fallback for
  scenes that don't fit.
- **Options if the limit becomes a real problem:**
  - Tiny paste-bin backend (Cloudflare Worker + KV, one endpoint,
    no auth) that stores gzipped JSON keyed by a short slug. Cheap,
    but breaks the "no backend" property of the current repo.
  - Compress harder: switch from `pako` deflate to Brotli via
    `CompressionStream('br')`. Modest gain (~10-20%), free.
  - Split share URL into a base scheme + separate "animation delta"
    file the user downloads alongside.
- **No accounts, no collection page, no server-side persistence** is
  a deliberate MVP choice. If we ever want cross-device "my scenes",
  the paste-bin option above is the smallest step that gets there.

## Authoring view

- **Split-view (top-down + perspective simultaneously).** MVP uses a
  single camera that swaps between orthographic top-down (author mode)
  and perspective first-person (playback / free-look). A synchronized
  split-view - e.g. top-down on the left, live 3D preview on the right,
  both updating as chips are dragged - would be nicer for authoring but
  adds a second renderer viewport and doubles per-frame render cost.
  Revisit if authoring feels blind.
- **Isometric authoring camera** as a third option, between top-down
  and full 3D. Follow-up.

## Timeline UI

- MVP: horizontally scrolling frame strip with mouse-wheel zoom, since
  "enjoyable video" length implies 10-40 keyframes and won't fit
  fit-to-width on smaller screens.
- Follow-up: **frame thumbnails** (render each frame's top-down view
  into a small canvas). Expensive to keep in sync during authoring but
  huge usability win. Consider lazy generation on hover.
- Follow-up: **per-element timeline tracks** (one row per chip showing
  its keyframes), like a real animation tool. Only worth it if users
  ask for it.

## Export

- **GIF as a first-class format.** MVP treats GIF as opt-in for short
  clips only, because the palette looks bad on the coloured rink and
  files get huge. If demand appears, revisit with a better quantizer
  (e.g. `gifski` compiled to WASM) instead of `gif.js`.
- **MP4 encoding on mobile.** WebCodecs is available on modern iOS/
  Android but 1080p60 encoding will be slow and hot on a phone. MVP
  keeps the same defaults everywhere; follow-up is to auto-lower
  default resolution/fps on `pointer: coarse` devices and warn.
- **Server-side render fallback.** If a user's browser has neither
  `VideoEncoder` nor `MediaRecorder` (very rare in 2026), MVP simply
  disables video export. Follow-up would be a tiny stateless render
  worker, but only if this ever affects a real user.

## Nice-to-have features not in the milestone list

- **Roster import** - load a team's player names + numbers from JSON
  so chips show real names instead of just numbers.
- **Multiple balls / pucks in one scene** - already supported by the
  data model, needs UI palette entries.
- **Shape templates / snippets** - save a curved-arrow style and
  reuse it. Follow-up once the shape tools are stable.
- **Import tactical-board.com JSON.** The reference plan's Doc/Scene
  model maps ~1:1 to ours minus the coord scale. One-shot converter,
  low effort, high goodwill if any users are migrating.
- **Voiceover / narration track** synced to the animation. Would
  require re-encoding audio into the MP4 - non-trivial but not huge.

## Deferred technical debt

- **Rink-constants extraction.** `RINK_L`, `RINK_W`, face-off dot
  positions etc. are already duplicated across `generators/*.py`
  (called out in `CLAUDE.md`) and will now also live in JS. Extracting
  a single `rink-spec.json` generated by one Python script, consumed
  by all other generators + the JS runtime, would fix both problems.
  Do this before authoring code hard-codes any dimension it shouldn't.
- **Bundler.** Still not needed. Revisit only if we start pulling in
  npm packages that don't ship ESM-on-CDN builds.
